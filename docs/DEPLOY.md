# Deploying: frontend on Vercel, backend on Render

Four things run in production, and only two of them are on Render:

| Piece | Where | Plan | Cost |
|---|---|---|---|
| Frontend (Next.js) | Vercel | Hobby | $0 |
| API **and** worker pool | Render web service | Standard (2 GB) | ~$25/mo |
| Redis (queue, analytics, enterprise) | Render Key Value | Starter | ~$10/mo |
| Qdrant (the product catalog) | Qdrant Cloud | Free (1 GB) | $0 |
| Disk for uploads + model cache | Render disk, 10 GB | — | ~$2.50/mo |

Roughly **$38/month**. The free tier cannot run this — see
[Why not the free tier](#why-not-the-free-tier).

Everything on Render is declared in `render.yaml` at the repo root; you
should not have to create services by hand.

---

## Before you start

You need three accounts: Vercel, Render, and Qdrant Cloud. Deploy in this
order — the backend needs Qdrant's URL, and the frontend needs the backend's.

---

## 1. Qdrant Cloud

The product catalog lives here. This project has **no SQL database at all**
— products are stored as Qdrant payloads alongside their vectors — so this
cluster is the system of record. Losing it loses the catalog.

1. Create a free cluster (1 GB) at <https://cloud.qdrant.io>.
2. Copy the **cluster URL** (it includes the port, e.g.
   `https://xxxxxxxx.us-east.aws.cloud.qdrant.io:6333`).
3. Create an **API key** and copy it. You will not see it again.

The two collections (`product_images`, `product_text`) are created
automatically on first use — you do not need to pre-create them.

## 2. Render

1. Push this branch to GitHub.
2. In Render: **New → Blueprint**, point it at the repo. It reads
   `render.yaml` and proposes `pi-backend` (web) and `pi-keyvalue`.
3. Render prompts for the three values marked `sync: false`:

   | Variable | Value |
   |---|---|
   | `VECTOR_STORE__URL` | the Qdrant cluster URL from step 1 |
   | `VECTOR_STORE__API_KEY` | the Qdrant API key from step 1 |
   | `APPLICATION__TRUSTED_HOSTS` | `["pi-backend.onrender.com"]` — see below |

   `SECURITY__SECRET_KEY` is generated by Render; you never supply it.

4. Apply. First build is slow (PyTorch is a large install) and the first
   boot downloads ~730 MB of models.

### `APPLICATION__TRUSTED_HOSTS` is not optional

`TrustedHostMiddleware` is the **outermost** middleware
(`backend/app/application.py`), so any request whose `Host` header is not in
this list is rejected with 400 before it reaches a route — including
Render's own health check, which will fail the deploy.

It must be a **JSON array literal** containing your actual Render hostname:

```
["pi-backend.onrender.com"]
```

Chicken-and-egg: you don't know the hostname until the service exists. If
Render won't let you leave it blank, put the expected value in — it follows
`<service-name>.onrender.com` — and correct it after the first deploy if it
differs.

### Watch the first boot for a permissions error

This is the most likely way the first deploy fails.

The image runs as an unprivileged user (`uid 10001`), and the disk is
mounted at `/app/storage`. The app then calls `mkdir` under it
(`UploadService`) and Hugging Face writes the model cache there. If Render
mounts the disk root-owned, all of that fails with `PermissionError` or
`OSError: [Errno 13]`.

If you see that in the logs, the fix is to chown the mount once at startup.
Add to `backend/scripts/start_all.py`, before spawning the children — it
needs the container to run as root, so it is deliberately *not* in there by
default:

```python
os.makedirs("/app/storage/uploads", exist_ok=True)
```

…or, more simply, drop the `USER app` line from `backend/Dockerfile`. That
trades a real security property for convenience, so only do it if the
managed alternative doesn't work.

## 3. Vercel

1. **New Project** → import the same repo.
2. Set **Root Directory** to `frontend`. This is a monorepo; without it
   Vercel builds the wrong thing.
3. Framework preset should auto-detect as Next.js. Leave the build command
   alone.
4. Add one environment variable:

   | Variable | Value |
   |---|---|
   | `BACKEND_ORIGIN` | `https://pi-backend.onrender.com` (no trailing slash) |

5. Deploy.

That single variable is the whole integration. `frontend/next.config.ts`
rewrites `/api/v1/*`, `/health`, `/ready` and `/version` to `BACKEND_ORIGIN`
**server-side**, so the browser only ever talks to the Vercel origin. Two
consequences worth knowing:

- **You never need to configure CORS on the backend.** Requests reach Render
  from Vercel's server, not from a browser, so they are not cross-origin.
  `APPLICATION__CORS_ALLOWED_ORIGINS` stays empty.
- **A backend failure shows up as a 500 from your Vercel domain**, not as a
  CORS error in the console. If the UI shell renders but every card fails,
  look at Render's logs, not Vercel's.

## Verifying it

```bash
curl https://pi-backend.onrender.com/health
curl https://pi-backend.onrender.com/api/v1/system/health
```

The second should report `redis: healthy` and `qdrant: healthy`. Then load
the Vercel URL and check the Dashboard **System** card shows the same.

To prove the worker really works — which is the one thing a green health
check does *not* tell you — upload an image through `/upload` and watch it
reach a product page. `workers: 4` in the health payload is configured
concurrency and reads the same whether or not a worker process is alive;
`queue_depth` climbing while nothing completes is what indicates a dead
worker.

The repo's driver script can do this against the deployed site:

```bash
BASE_URL=https://your-app.vercel.app node .claude/skills/run-app/scripts/drive.js --upload
```

## Things that will bite you

**Cold starts are slow.** The image imports PyTorch and loads three models
at boot. Render's health check `start-period` accounts for this, but expect
a minute or more before the service answers. Model weights are cached on the
disk (`HF_HOME=/app/storage/hf-cache`), so this is only genuinely painful on
the very first boot and after a disk change — not on every deploy.

**Redis holds real data, not just a cache.** The queue, analytics counters,
enterprise records and the recommendation cache all live there. That is why
`render.yaml` sets `maxmemoryPolicy: noeviction` and uses a paid plan: an
LRU policy would silently evict queued jobs, and the free plan does not
persist at all. If you downgrade to free, expect the catalog's *history* to
reset on every restart — the catalog itself survives, because it is in
Qdrant.

**The API and worker share one instance and one disk.** That is forced, not
chosen: the API writes an upload, the worker reads that exact path, and the
API serves it back. A Render disk is reachable by exactly one service, so
the two roles cannot be split without moving uploads to object storage
(S3/R2). `backend/scripts/start_all.py` documents the trade in full. The
practical consequences: no independent scaling, a single instance ceiling,
and no zero-downtime deploys.

**Deploys drop in-flight jobs gracefully, not instantly.** SIGTERM reaches
both children; uvicorn drains requests and the worker finishes its current
job. Jobs still queued survive in Redis and are picked up by the new
instance.

**`APPLICATION__ENVIRONMENT` is `staging`, not `production`.** That is
deliberate and matches `docker-compose.prod.yml`'s reasoning:
`Settings._validate_production_safety` refuses to boot in `production`
unless `DATABASE__URL` is non-SQLite, but this project has no relational
database — `settings.database` is referenced nowhere outside a docstring.
Choosing `production` would mean inventing a Postgres URL that nothing
connects to purely to satisfy a validator. Everything that validator
protects (secret key, debug off, non-wildcard trusted hosts) is set
explicitly in `render.yaml` regardless.

## Why not the free tier

Render's free web service is **512 MB RAM and 0.1 CPU**, and spins down
after 15 minutes of inactivity. This backend loads PyTorch plus CLIP
(~600 MB), BGE (~130 MB) and a cross-encoder — and loads them twice, once
per child process. It will OOM before it finishes booting, and 0.1 CPU would
make embedding inference unusable even if it fit.

Render's free Key Value is in-memory only with no persistence, losing all
data on restart.

If cost is the binding constraint, the lever with real leverage is dropping
the local models for a hosted embedding API, which removes the 2 GB floor
entirely. That is an application change, not a deployment one.
